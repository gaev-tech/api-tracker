# Продуктовое описание

## 1. Назначение

1.1 Личный (с возможностью эволюции в командный) трекер задач, оптимизированный под управление через AI-агентов.

1.2 Управление состоянием системы осуществляется исключительно через CLI; публичного HTTP-API для конечных пользователей нет.

1.3 Браузерные клиенты (см. 3.2, 3.3) не предназначены для управления задачами и не содержат для этого UI.

## 2. Ценностное предложение

2.1 Целевой сценарий использования — оркестрация AI-агента, который ведёт задачи от имени пользователя.

2.2 Принципы дизайна, вытекающие из 2.1:

2.2.1 CLI-интерфейс — родная форма взаимодействия для AI-агента.

2.2.2 RSQL-фильтрация задач — детерминированный машинно-читаемый язык запросов.

2.2.3 Bulk- и Batch-операции — массовые мутации одним вызовом для эффективности агента.

2.2.4 JSON-массовое создание задач (см. 7.6) — формат, в котором LLM нативно генерирует данные.

2.2.5 Гранулярные права (см. 6) — программируемая политика доступа.

2.2.6 Cron-автоматизация и webhook (см. 8) — интеграция с внешним AI-пайплайном.

2.2.7 Audit-log (см. 9) — агент читает историю своих действий и принимает решения на её основе.

2.2.8 Отсутствие богатого UI — агенту он не нужен; ресурсы фокусируются на качестве API и CLI.

## 3. Клиенты

3.1 CLI-клиент `apit` — Python, основной интерфейс к системе.

3.1.1 Распространяется в виде platform-binaries (macOS, Linux, Windows) через отдельный публичный GitHub-репозиторий и через основные пакетные площадки экосистем (PyPI, Homebrew, APT, npm) — см. `architecture.md` §15.8, §15.9.

3.2 Auth-клиент — Angular SPA на `auth.apitracker.ru`, единственная задача — первичная аутентификация пользователя и подтверждение CLI-handoff (см. 10).

3.3 Docs-клиент — Angular SPA на `docs.apitracker.ru`, читаемая справка по CLI, RSQL, схеме данных, событиям, system-методам и туториалы.

3.4 Корневой домен `apitracker.ru` редиректит на 3.3.

## 4. Пользователи

4.1 Все пользователи системы равноправны на уровне продукта; разграничение полномочий — только через права на конкретные сущности (см. 6).

4.2 Системных ролей "администратор" нет; нет глобальных привилегий, не зависящих от прав на сущности.

## 5. Доменная модель

### 5.1 Сущности

5.1.1 Пользователь — субъект, имеющий email и доступ через 3.1 или 3.2.

5.1.2 Задача — единица работы со следующими полями:

5.1.2.1 Название (обязательное).

5.1.2.2 Описание в формате Markdown.

5.1.2.3 Массив текстовых меток.

5.1.2.4 Ответственный — один пользователь, имеющий доступ к задаче.

5.1.2.5 Статус — `open` | `done` | `archived`.

5.1.2.6 Список блокирующих задач — задачи, без выполнения которых данная не может быть завершена.

5.1.2.7 Список прямого шаринга пользователям с правами (см. 6.3).

5.1.2.8 Список прямого шаринга командам с правами (см. 6.3).

5.1.2.9 Список проектов, в которые задача добавлена (см. 5.1.4).

5.1.3 Команда — именованный набор пользователей; команда сама по себе не даёт никаких прав на задачи или проекты.

5.1.4 Проект — именованная коллекция задач и список пользователей и команд с правами в проекте.

5.1.5 Автоматизация — правило, привязанное к проекту (см. 8).

5.1.6 Секрет проекта — именованная пара (имя → зашифрованное значение), используемая в автоматизациях (см. 8.7).

5.1.7 Событие истории — запись о действии пользователя над сущностью (см. 9).

### 5.2 Идентификаторы

5.2.1 Пользователь — идентифицируется по email во внешнем взаимодействии (CLI-параметры, шаринг).

5.2.2 Команда — идентифицируется UUID; имя команды не уникально и не используется как идентификатор.

5.2.3 Проект — идентифицируется UUID; имя проекта не уникально.

5.2.4 Задача — идентифицируется UUID.

5.2.5 Автоматизация и секрет — идентифицируются UUID в рамках проекта.

## 6. Права и инварианты доступа

### 6.1 Базовые инварианты

6.1.1 Membership = наличие ≥1 разрешения. Пользователь считается участником команды/проекта/задачи тогда и только тогда, когда у него хотя бы одно разрешение в данной сущности.

6.1.2 Добавление участника = установка непустого массива разрешений пользователю, у которого был пустой массив.

6.1.3 Удаление участника = установка пустого массива разрешений.

6.1.4 Self-revoke всегда доступен. Любой пользователь в любой момент может установить свой собственный массив разрешений в пустой (выйти из команды/проекта, удалить свой доступ к задаче).

6.1.5 Lifecycle сущности: команда, проект или задача существуют, пока ≥1 пользователь имеет ≥1 разрешение в этой сущности или (для задачи) пока задача принадлежит ≥1 проекту с участниками.

6.1.6 Каскад удаления: при потере последнего участника или принадлежности сущность удаляется автоматически вместе со всеми зависимыми записями.

6.1.7 Share-not-above-self: при выдаче или изменении разрешений другого участника (через `share` или `manage_member_permissions`) нельзя дать больше, чем имеешь сам в данной сущности.

6.1.8 Чтение неявно: при наличии ≥1 любого разрешения в сущности пользователь имеет право её читать; отдельного `read` разрешения не существует.

### 6.2 Эффективные права на задачу

6.2.1 Эффективные права пользователя U на задачу T = объединение двух путей:

6.2.1.1 Path A — прямой шаринг задачи: разрешения U в `TaskUserShare(T, U)` объединённые с разрешениями U через `TaskTeamShare(T, team)` для каждой команды, в которой U состоит.

6.2.1.2 Path B — членство в проекте: для каждого проекта P, содержащего T, разрешения U в `ProjectUserMember(P, U)` объединённые с разрешениями U через `ProjectTeamMember(P, team)` для каждой команды, в которой U состоит.

### 6.3 Разрешения задачи (гранулярные флаги)

6.3.1 `edit_title` — изменение названия (см. 5.1.2.1).

6.3.2 `edit_description` — изменение описания (см. 5.1.2.2).

6.3.3 `edit_labels` — изменение массива меток (см. 5.1.2.3).

6.3.4 `edit_blockers` — изменение списка блокирующих задач (см. 5.1.2.6).

6.3.5 `edit_status` — изменение статуса (см. 5.1.2.5).

6.3.6 `edit_assignee` — изменение ответственного (см. 5.1.2.4).

6.3.7 `manage_projects` — добавление и удаление задачи из проектов.

6.3.8 `share` — выдача и изменение разрешений другим участникам задачи (с учётом 6.1.7).

### 6.4 Разрешения команды

6.4.1 `edit_team_name` — изменение имени команды.

6.4.2 `manage_member_permissions` — изменение состава разрешений других участников команды (включая добавление новых через 6.1.2 и удаление через 6.1.3).

### 6.5 Разрешения проекта

6.5.1 `edit_project_name` — изменение имени проекта.

6.5.2 `manage_member_permissions` — аналогично 6.4.2 для проекта.

6.5.3 `manage_automations` — создание, изменение, удаление автоматизаций проекта (см. 8).

6.5.4 `manage_secrets` — создание, изменение, удаление секретов проекта (см. 5.1.6).

6.5.5 Все разрешения задачи 6.3.1–6.3.8, применяемые к каждой задаче, состоящей в данном проекте, для каждого участника проекта.

### 6.6 Anchor-rule при создании задачи

6.6.1 Запрос на создание задачи обязан содержать хотя бы один из якорей:

6.6.1.1 `projects` — непустой список UUID проектов, в одном из которых создатель имеет `manage_projects` (см. 6.5.5).

6.6.1.2 `user_shares` — непустой список, включающий самого создателя с непустым массивом разрешений.

6.6.1.3 `team_shares` — непустой список, включающий команду, в которой создатель состоит, с непустым массивом разрешений.

6.6.2 Назначение 6.6.1 — задача не может быть создана без участника, иначе сработал бы каскад 6.1.6 в момент создания.

### 6.7 Ограничения шаринга

6.7.1 Шарить задачу команде можно, только если шарящий сам состоит в этой команде (вытекает из 6.1.7: вне команды у субъекта нет прав-уровня).

6.7.2 Добавлять команду в проект можно по тому же правилу.

## 7. Способы взаимодействия

### 7.1 Список задач по RSQL-фильтру

7.1.1 `apit task list --filter <rsql>` возвращает страницу задач, отсортированных по `created_at` возрастанию.

7.1.2 Пагинация курсорная, лимит по умолчанию 50, максимум 200.

7.1.3 RSQL поддерживает операторы: `==`, `!=`, `=gt=`, `=ge=`, `=lt=`, `=le=`, `=in=(...)`, `=out=(...)`, логические `;` (and), `,` (or), скобки.

7.1.4 Литерал `me` в правой части `==` или `=in=` для полей `assignee` и `share_owner` резолвится в email текущего пользователя.

### 7.2 Bulk-изменение по RSQL-фильтру

7.2.1 Семантика — частичный успех: операция применяется к каждой задаче, попавшей в фильтр, независимо; ошибки на одних задачах не откатывают изменения на других.

7.2.2 Ответ содержит per-задачный статус: `ok`, `forbidden`, `validation_failed`, `not_found`.

### 7.3 Batch-изменение по RSQL-фильтру

7.3.1 Семантика — атомарность: либо все попавшие задачи получают изменение, либо ни одна; первая же ошибка прав или валидации отменяет всю операцию.

7.3.2 При неуспехе ответ содержит причину и идентификатор задачи, на которой произошёл отказ.

### 7.4 Изменение разрешений пользователя в команде или проекте

7.4.1 Адресуется по email пользователя.

7.4.2 Установка непустого массива при пустом исходном эквивалентна добавлению (см. 6.1.2).

7.4.3 Установка пустого массива эквивалентна удалению (см. 6.1.3).

7.4.4 Ограничение 6.1.7 проверяется на сервере.

### 7.5 Получение данных по проекту и команде

7.5.1 Возможно при наличии любого ≥1 разрешения в сущности (см. 6.1.8).

7.5.2 Включает: основные поля сущности, список участников с их разрешениями, для проекта — список задач (только тех, которые видны пользователю по 6.2).

### 7.6 Массовое создание задач JSON

7.6.1 `apit task bulk-create --from <file.json>` принимает массив объектов задач.

7.6.2 Каждый элемент массива обязан удовлетворять 6.6.

7.6.3 Доступны bulk-семантика (см. 7.2.1) и batch-семантика (см. 7.3.1) — команды `bulk-create` и `batch-create`.

### 7.7 Массовое создание задач CSV

7.7.1 Рассматривается как workaround массового создания JSON (см. 7.6).

7.7.2 Не входит в M1 (см. `implementation-plan.md` §3); планируется как PostMVP.

### 7.8 Self-revoke

7.8.1 `apit share user remove <task-uuid> --self` — удалить свой доступ к задаче.

7.8.2 `apit team leave <team-uuid>` — выйти из команды.

7.8.3 `apit project leave <project-uuid>` — выйти из проекта.

## 8. Автоматизации

8.1 Автоматизация — правило, привязанное к одному проекту (см. 5.1.5).

8.2 Управляется через право проекта `manage_automations` (см. 6.5.3).

8.3 Автоматизация состоит из триггера и действия.

### 8.4 Триггеры

8.4.1 `event` — реактивный триггер; срабатывает при событии в задаче проекта, удовлетворяющей RSQL-фильтру.

8.4.1.1 Поля: `event_type` (см. 8.4.3), `filter` (RSQL).

8.4.2 `cron` — расписанный триггер; срабатывает по cron-выражению.

8.4.2.1 Поля: `cron` (стандартное 5-полевое выражение).

8.4.3 Каталог `event_type` фиксируется в схеме (см. `architecture.md` §11) и рендерится в docs-client.

### 8.5 Действия

8.5.1 `webhook` — отправка HTTP POST на внешний URL.

8.5.1.1 Поля: `url`, `headers`, `body` (Jinja-шаблон).

8.5.1.2 Шаблон может ссылаться на `{{secrets.<name>}}` (см. 8.7) и на контекст триггера (`task.*` для event, `query(...)` для cron).

8.5.2 `system_method` — вызов внутреннего метода системы.

8.5.2.1 Поля: `method` (строка из whitelist), `args` (Jinja-шаблон).

8.5.2.2 Whitelist методов фиксируется в `architecture.md` §11.4.

### 8.6 Доставка webhook

8.6.1 Попытки с экспоненциальным бэкоффом до 5 раз.

8.6.2 При исчерпании попыток — отметка в dead-letter (см. `architecture.md` §12).

### 8.7 Секреты проекта

8.7.1 Хранятся зашифрованными в БД (см. `architecture.md` §13).

8.7.2 Управляются через право `manage_secrets` (см. 6.5.4).

8.7.3 Используются исключительно в шаблонах действий автоматизаций (см. 8.5.1.2).

## 9. История изменений

9.1 Каждая мутация в системе порождает запись истории.

9.2 Запись содержит: автора (email), тип цели (task/team/project/...), идентификатор цели, тип события, дифф изменённых полей, временную метку.

9.3 `apit history task <uuid>` — история конкретной задачи (доступна при праве чтения задачи, см. 6.1.8).

9.4 `apit history user <email>` — действия пользователя (доступна каждому пользователю в отношении самого себя; в отношении других — см. `architecture.md` §10.2.2).

9.5 Пагинация курсорная, лимит фиксированный 50, переопределение лимита не поддерживается.

9.6 Фильтры — только `user_id` или `task_id`; RSQL по истории не поддерживается.

## 10. Регистрация и аутентификация

10.1 Регистрация открытая: любой email может запросить вход.

10.2 Метод входа — magic-link на email; отдельной формы регистрации нет.

10.3 Пароли в системе отсутствуют.

10.4 Подтверждение email не требуется; первый успешный magic-link создаёт пользователя.

10.5 CLI получает токен через handoff в браузер (см. `architecture.md` §4).

## 11. Не-функциональные требования

11.1 Авто-деплой на прод при push в `main` (см. `architecture.md` §17, §18).

11.2 Все Python-сервисы и CLI — Python > 3.5 (минимум 3.6) с обязательными аннотациями типов (см. `architecture.md` §19).

11.3 OpenAPI и protobuf — единый источник правды для контрактов, фронт генерируется кодогеном (см. `architecture.md` §5).

11.4 Резервное копирование БД ежедневно с ротацией 14 дней (см. `architecture.md` §3.4).

11.5 CLI публикуется в отдельный публичный GitHub-репозиторий (см. `architecture.md` §15.8); основной monorepo с исходниками всех сервисов остаётся приватным.

11.6 CLI также публикуется в основные пакетные площадки: PyPI, Homebrew, APT, npm (см. `architecture.md` §15.9). Единственный источник бинарей — GitHub Releases из §15.8; остальные площадки оборачивают или ссылаются на эти бинари.

## 12. Не входит в скоуп MVP

12.1 Тарифные лимиты, фриз сущностей по лимитам.

12.2 Уведомления (email/in-app) — пользователи реализуют их через webhook-автоматизации.

12.3 Сроки выполнения задач (due dates).

12.4 Комментарии к задачам.

12.5 Recurring tasks как отдельная сущность (моделируется через cron-автоматизацию).

12.6 Изменение email пользователя.

12.7 CSV-импорт (см. 7.7).

12.8 Публичное HTTP-API для третьих сторон.

12.9 In-app inbox (см. 12.2).
